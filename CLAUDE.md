# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A Home Assistant **custom integration** (HACS) for SMA solar inverters with
**SMA Bluetooth** (Bluetooth Classic, RFCOMM channel 1). The protocol code is a
Python port of [SBFspot](https://github.com/SBFspot/SBFspot)'s Bluetooth path.

Home Assistant runs in a Hyper-V VM with no Bluetooth. ESPHome Bluetooth
proxies are BLE-only and cannot carry RFCOMM. So a dedicated **original ESP32**
(WROOM/WROVER; S2/S3/C3/C6/H2 have no BR/EDR) runs an ESPHome component that
bridges TCP to the inverter's Bluetooth link:

```
Home Assistant --TCP:9900--> ESP32 (sma_bt_bridge) --BT Classic SPP--> SMA inverter
  (all protocol logic)         (transparent pipe)
```

Verified hardware: SMA **SB 3000TL-20**, firmware 03.20.01.R, single phase,
one DC string (phases 2/3 and string B report NaN -> `None`).

## Layout

- `custom_components/sbfspot/smabt/` — **protocol client.** Standard library
  only, asyncio streams only, **no `homeassistant` imports**, intra-package
  imports relative (guard tests enforce this). `frame.py` (L1 Bluetooth frames,
  escaping, FCS-16, L2 header), `parse.py` (records, NaN sentinels, units),
  `client.py` (`SmaBluetoothClient`, `async_read_inverter`), `transport.py`
  (`BridgeTransport`), `const.py`, `models.py`, `errors.py`, `tag_names.py`
  (generated by `scripts/gen_tag_names.py` from SBFspot's `TagListEN-US.txt`;
  do not edit by hand).
- `custom_components/sbfspot/` (rest) — **HA layer**: config flow (user,
  reconfigure, reauth, options), coordinator, entities, diagnostics.
- `esphome/components/sma_bt_bridge/` — **ESP32 bridge firmware** (ESP-IDF
  Bluedroid SPP + ESPHome sockets). `bridge_protocol.h` is pure C++17 (host
  tested). `esphome/sma-bt-bridge.yaml` is the example device config.
- `scripts/` — `read_inverter.py` (CLI end-to-end hardware test through a
  bridge), `sanitize_capture.py`, `gen_tag_names.py`, `make_brand_icons.py`.
- `tests/` — protocol + guard tests (any OS); `tests/ha/` — HA tests (Linux);
  `esphome/tests/` — bridge host tests and simulation.

## Data flow

Each poll is one complete SBFspot-style session: open transport -> bridge
handshake -> inverter hello / topology -> BT signal query -> logon (user group)
-> device info + spot queries (SBFspot's order) -> logoff -> **close transport
in `finally`**. No connection is held between polls.

## Bridge protocol v1 (two implementations, change both together)

Python side: `smabt/transport.py` docstring. Firmware side:
`esphome/components/sma_bt_bridge/bridge_protocol.h`. Summary:

1. Bridge greets `SMABT 1\n` (or `ERR BUSY ...\n` and closes).
2. Client sends `CONNECT AA:BB:CC:DD:EE:FF\n` within 5 s.
3. Bridge replies `OK <ESP32 BT MAC>\n` then pipes bytes, or
   `ERR <BAD_REQUEST|BT_CONNECT_FAILED|BT_TIMEOUT|BUSY> <text>\n` and closes.
4. Either side closing ends the session. Right after a session the bridge may
   answer `ERR BUSY` briefly; `BridgeTransport.open()` retries for ~6 s.

Any change to this protocol needs a new greeting version and matching tests on
both sides.

## Critical invariants

- **Night is normal.** The inverter's Bluetooth sleeps without sun. Connection
  errors (`SmaConnectionError` and subclasses) give *offline* data, never
  `UpdateFailed`. Setup at night must succeed. The coordinator does not poll
  outside sunrise − 15 min .. sunset + 15 min (SBFspot `SunRSOffset=900`).
- **TOTAL_INCREASING sensors never report 0 or go down.** `energy_total`,
  `operating_time`, `feed_in_time` keep the last valid value (persisted with
  `Store`) when offline and when the inverter returns NaN/0/a lower value.
  `energy_today` keeps its value until local midnight, then 0. A wrong 0
  permanently corrupts long-term statistics. Tests in `tests/ha/` lock this —
  extend them, never relax them.
- **Auth errors** (`SmaAuthError`) raise `ConfigEntryAuthFailed` (reauth flow).
- **Fixtures are sanitized real captures.** `tests/fixtures/sb3000tl20_session.json`
  came from a real SBFspot `-d5` session. It must never contain the real
  inverter MAC, adapter MAC, serial or password.

## Sensitive data — hard rules

- Never commit SBFspot install files. `SBFspot.cfg` holds the inverter
  password and Bluetooth address. `.gitignore` blocks `*.cfg`, `*.exe`,
  `*.dll`, `*.rar`.
- Never commit raw capture logs. Make a new fixture only through
  `scripts/sanitize_capture.py`, then scan the repo for the real values before
  you commit.
- To capture a new session on a Windows PC in Bluetooth range: copy
  `SBFspot.cfg`, set `SynchTime=0` (no clock writes), then run
  `SBFspot.exe -d5 -v5 -nocsv -nosql -ad0 -am0 -ae0 -finq -cfg:<copy>` and
  redirect the output to a file outside the repo.

## Adding a sensor

1. Make sure `smabt` produces the value (add a parse test against a real
   capture first).
2. Add the `SensorEntityDescription` in `sensor.py` with a `translation_key`.
3. Add the name to `strings.json` **and** `translations/en.json` (identical
   files). `tests/test_sensor_consistency.py` fails if they drift.
4. If it is cumulative: `TOTAL_INCREASING` + add it to the coordinator's
   preserved keys + extend the invariant tests.

## Development

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[test,dev]"   # Windows
```

- Protocol + guard tests (Windows OK): `.venv/Scripts/python -m pytest tests --ignore=tests/ha -q`
- HA tests (Linux/WSL only; harness needs uvloop): in WSL,
  `uv venv .venv-wsl --python 3.14`, `uv pip install --python .venv-wsl/bin/python -e ".[test,test-ha]"`,
  then `.venv-wsl/bin/python -m pytest tests/ha -q`. Use Python 3.14: on 3.13
  pip resolves HA 2026.2, below our 2026.3 minimum. Run `tests/ha` on its own
  in that env — the HA plugin blocks the sockets the top-level tests use.
- Lint (CI gate): `ruff check . && ruff format --check .`
- Bridge host tests (WSL/Linux): `g++ -std=c++17 -Wall -Wextra -Werror esphome/tests/test_bridge_protocol.cpp -o /tmp/tbp && /tmp/tbp`,
  then `bash esphome/tests/sim/run.sh` (plain + ASan/UBSan; add `tsan` to run TSan).
- Firmware compile: `esphome compile esphome/sma-bt-bridge.yaml` after
  `cp esphome/secrets.example.yaml esphome/secrets.yaml`. On Windows run it
  from **PowerShell**, not Git Bash (ESP-IDF refuses MSys). Uses ESPHome
  2026.10 APIs; the `esphome` CI job is the source of truth for API drift.
- Real hardware, no HA: `python scripts/read_inverter.py --bridge HOST[:PORT] --bt AA:BB:CC:DD:EE:FF -v`.

CI (`.github/workflows/ci.yml`): `lint`, `test-client`, `test-ha`, `hacs`,
`hassfest`, `esphome` (compile), `bridge-protocol` (host tests + sim).

## Workflow rules

- **Branch and PR.** Never commit or push to `main`. One branch per change;
  open a PR with `gh pr create`; the user merges.
- **Code is written by Sonnet agents.** Claude designs, writes a tight brief
  (files owned, contract, real tests to write), reviews and integrates. Briefs
  always include real tests: real captures and real sockets, not tautologies.
- **TDD.** Failing test first, then the code. Never change a test just to make
  code pass; discuss it first.
- **Communication with the user:** ASD-STE100 Simplified Technical English.
  Short and to the point.
- **Do not invent features.** Out of scope until the user asks: Speedwire/
  Ethernet, multi-inverter Bluetooth nets (MIS / NetID > 1), archive (day/month)
  data, events, battery inverters, installer logon, local-adapter RFCOMM
  transport (a `Transport` subclass would make this easy — ask first).

## Releasing

Bump `version` in `custom_components/sbfspot/manifest.json` **and**
`pyproject.toml` in the same PR as the change (`tests/test_manifest.py`
checks they match). Check `git tag` and `gh release list` first so you pick a
free number. After merge, create tag `vX.Y.Z` and a GitHub release (HACS needs
a release). The user pushes tags.
